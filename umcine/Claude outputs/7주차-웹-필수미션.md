# ✅ 7주차 웹 필수 미션 - 로그인과 내 정보 화면 퍼블리싱하기

## 📌 미션 요약
본문에서 만든 회원가입 화면에 이어, 디자인에 맞춰 **로그인**, **내 정보 조회**, **내 정보 수정** 화면을 만든다. 각 페이지에 접속해 화면이 보이고 입력한 값이 반영되는지 확인한다.

## 🧾 핵심 코드

### 공통: 폼 필드 (`components/form/form-field.tsx`)
라벨 + 입력 + (오른쪽 버튼) + 안내/오류 문구를 디자인과 같은 간격으로 묶는다. 네 화면이 모두 이 컴포넌트를 쓴다.
```tsx
export function FormField({ id, label, hint, error, action, children }: FormFieldProps) {
  return (
    <div className="flex flex-col gap-1.5">
      <label htmlFor={id} className="text-xs font-bold text-text-primary">{label}</label>
      <div className="flex gap-2">
        {children}
        {action}
      </div>
      {error ? <p className="text-xs text-danger-default" role="alert">{error}</p>
             : hint ? <p className="text-xs text-text-tertiary">{hint}</p> : null}
    </div>
  );
}
```

### 검증 규칙 (`utils/validators.ts`)
```ts
export const EMAIL_REGEX = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
// 영문 대소문자, 숫자, 특수문자(!@#$%^&*)를 모두 포함해 8자 이상 (백엔드 SignUpRequest의 @Pattern과 같은 규칙)
export const PASSWORD_REGEX = /^(?=.*[a-z])(?=.*[A-Z])(?=.*[0-9])(?=.*[!@#$%^&*])[A-Za-z0-9!@#$%^&*]{8,}$/;
export const isValidEmail = (v: string) => EMAIL_REGEX.test(v.trim());
export const isValidNickname = (v: string) => v.trim().length >= 2 && v.trim().length <= 12;
export const isValidPassword = (v: string) => PASSWORD_REGEX.test(v);
```
프론트의 규칙과 백엔드 DTO의 규칙을 같게 맞춰 두면, 화면에서 통과한 값이 서버의 400으로 튕기는 일이 줄어든다. 그래도 서버 검증은 그대로 둔다(화면은 우회할 수 있으니까).

### 회원가입 (`pages/auth/signup-page.tsx` 중)
```tsx
const [form, setForm] = useState(DEFAULT_FORM);
const [duplicateCheck, setDuplicateCheck] = useState({ email: DEFAULT_DUPLICATE_CHECK, nickname: DEFAULT_DUPLICATE_CHECK });
const [isSubmitting, setIsSubmitting] = useState(false);

const isFormValid = isEmailValid && isNicknameValid && isPasswordValid && isPasswordConfirmValid;
// 입력 조건과 두 중복 확인을 모두 통과해야 제출 가능
const canSubmit = isFormValid && duplicateCheck.email.isAvailable && duplicateCheck.nickname.isAvailable;

const handleChangeField = (key: DefaultFormKey, value: DefaultFormValue) => {
  if (key === "email" || key === "nickname") {
    if (duplicateCheck[key].isChecking) return;
    // 확인한 값을 바꾸면 다시 중복 확인해야 함
    setDuplicateCheck((prev) => ({ ...prev, [key]: DEFAULT_DUPLICATE_CHECK }));
  }
  setForm((prev) => ({ ...prev, [key]: value }));
};

const handleSubmit = async (event: SubmitEvent<HTMLFormElement>) => {
  event.preventDefault();
  if (!canSubmit || isSubmitting) return;
  setIsSubmitting(true);
  try {
    const response = await signup({ email: form.email.trim(), nickname: form.nickname.trim(), password: form.password });
    alert(response.message);
    setProfile({ email: response.result.email, nickname: response.result.nickname });
    navigate({ to: "/login" });
  } catch (error) {
    // 서버가 { isSuccess:false, code, message }를 돌려주면 그 message를 그대로 보여 줘요. (409 중복, 400 검증)
    if (isHTTPError(error)) {
      const body = await error.response.json<ApiEnvelope<null>>().catch(() => null);
      alert(body?.message ?? "회원가입에 실패했어요. 다시 시도해 주세요.");
    } else {
      alert("회원가입에 실패했어요. 다시 시도해 주세요.");
    }
  } finally {
    setIsSubmitting(false);
  }
};
```
- 워크북과 달리 실패 시 서버의 `message`("이미 사용 중인 이메일입니다." 등)를 그대로 보여 준다. 6주차 백엔드가 공통 응답 형식을 쓰기 때문에 가능하다.
- `passwordConfirm`은 화면에서만 검사하고 요청에 넣지 않는다.

### 임시 store (`stores/profile-store.ts`)
```ts
export const useProfileStore = create<ProfileState>()(
  persist(
    (set) => ({
      profile: null,
      setProfile: (profile) => set({ profile }),
      updateNickname: (nickname) =>
        set((state) => (state.profile ? { profile: { ...state.profile, nickname } } : state)),
      clearProfile: () => set({ profile: null }),
    }),
    { name: "umcine-profile-store", storage: createJSONStorage(() => localStorage) },
  ),
);
```
로그인·회원가입에서 입력한 값을 저장하고 조회·수정 화면이 읽는다. 8주차에 토큰과 `GET /members/me`가 생기면 이 store는 토큰 보관용으로 바뀐다.

## 🧯 트러블 슈팅

### 이슈 No.1 - 오류 문구가 나타나면 아래 입력이 밀려 클릭 위치가 어긋남
**이슈**
로그인 화면에서 잘못된 이메일을 입력한 상태로 비밀번호 칸을 눌렀는데 입력이 안 됐다.

**원인**
이메일 아래에 오류 문구(`<p role="alert">`)가 생기면서 비밀번호 입력이 14px 아래로 밀렸다. 자동화된 클릭 좌표가 원래 자리를 눌러서 문구를 클릭한 것이었다. 사용자가 직접 쓸 때는 문제없지만, 레이아웃이 입력 중에 움직이는 건 좋은 경험은 아니다.

**해결**
동작 자체는 정상이라 코드는 두고, `FormField`가 `hint`를 받으면 오류가 없을 때도 같은 자리에 안내 문구를 둬서 높이가 변하지 않게 했다(비밀번호 필드). 이메일처럼 안내가 없는 필드는 오류가 생길 때만 한 줄이 늘어난다.

**배운 점**
오류 문구는 "자리를 미리 확보할지"를 정해야 한다. 디자인에 안내 문구가 있는 필드는 그 자리를 오류 문구와 공유하면 흔들리지 않는다.

### 이슈 No.2 - `/my`(5주차)와 `/me`(7주차) 경로
**이슈**
5주차에 백엔드 연결 데모로 만든 `내 정보`(`/my`)와 7주차 디자인의 내 정보 화면이 겹쳤다.

**해결**
7주차 화면은 `/me`, `/me/edit`로 만들고 헤더의 `내 정보`를 `/me`로 바꿨다. `/my`는 5주차 기록용으로 남겨 뒀다. 8주차에 `GET /members/me`를 연결하면 `/me`가 실제 서버 데이터를 보여 주게 되고, 그때 `/my`를 정리한다.

## 💡 배운 점
- 폼 상태는 세 종류로 나뉜다. 입력값(`form`), 서버 확인 결과(`duplicateCheck`), 요청 진행 상태(`isSubmitting`). 이걸 한 state에 섞으면 "값을 바꾸면 확인 결과를 초기화한다" 같은 규칙을 적기 어렵다.
- 버튼 활성화 조건(`canSubmit`)을 계산값으로 두면 "언제 눌러도 되는가"가 한 줄에 드러난다.
- 백엔드가 공통 응답 형식을 지키면 프론트는 실패 응답의 `message`를 그대로 띄울 수 있다. 5·6주차에 정한 약속이 여기서 쓰였다.
- 같은 요청 상태 관리(진행 중, 성공, 실패)를 세 화면에서 반복했다. 8주차 `useMutation`이 이걸 줄여 줄 거라는 게 체감된다.
